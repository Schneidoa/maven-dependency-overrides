# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this plugin does

IntelliJ Platform plugin that flags Maven `<dependencyManagement>` version overrides that have become stale because an imported BOM chain has caught up (typical case: a CVE-driven pin that Spring Boot's BOM now provides at or above the pinned version). Detection reads whatever POMs are already in the user's local Maven repository and refuses to answer confidently when a BOM in the chain can't be resolved there (`Inconclusive` vs. `Confirmed`) — that refusal, and the correctness of a `Confirmed` verdict, never depend on the network. Detection itself is still correct entirely offline; what changed in Phase 9 is that the tool window, the Add/Edit dialogs, and the BOM chain view now try to fetch a missing BOM or parent POM from the remote repositories Maven itself would use before falling back to `Inconclusive`, so a POM that is merely absent rather than genuinely unverifiable no longer has to stay a refusal. The editor inspection is deliberately excluded from that and stays fully offline (see invariants below).

## Build & run

```bash
./gradlew check                # unit tests + platform tests (this is what .run/Run Tests wraps)
./gradlew test --tests "cloud.schneidoa.detection.OverrideDetectorTest"                       # single class
./gradlew test --tests "cloud.schneidoa.detection.OverrideDetectorTest.test*confirmed*"       # single test (backticked names → globs)
./gradlew runIde               # launch a sandbox IDE with the plugin loaded (for manual verification)
./gradlew verifyPlugin         # IntelliJ plugin-verifier compatibility check
```

Target platform is pinned in `build.gradle.kts` (`intellijIdea("2026.2.1")`). The `prepareTestSandbox` task disables the bundled Vue.js plugin — leave that in place; the comment there explains why, and TestLoggerFactory's "logged errors fail the test" behavior is deliberately kept on as a safety net.

## Branches and releases

Work goes on `develop`; `main` is the release branch and receives merges from `develop` only. `.github/workflows/build.yml` runs `check buildPlugin verifyPlugin` on every `develop` push and every PR into either branch. `.github/workflows/release.yml` runs on `main` and does the whole release: patch changelog → same build gate → `publishPlugin` → tag `v<version>` → GitHub Release → changelog PR back to `develop`.

Two things about that flow are load-bearing. **The `version` in `gradle.properties` is the entire release trigger**, and the `v<version>` tag is the idempotence guard: a push to `main` whose version is already tagged releases nothing and reports as skipped, which is what makes merging a docs fix into `main` harmless. The tag is therefore written *after* a successful Marketplace upload, never before — a tag on a release that didn't happen would silently block the retry. **A version with a pre-release suffix routes itself**: `channels` in `build.gradle.kts` sends `0.3.0-beta.1` to the `eap` channel and a plain `0.3.0` to the default one, and the workflow marks the GitHub Release accordingly. Both halves read the same `-` in the version string; changing one without the other splits the two apart.

## Architecture

Package `cloud.schneidoa` splits into two layers with a hard rule: everything under `resolver/` must stay free of IntelliJ Platform APIs so it stays unit-testable against fixture POMs; anything that touches PSI/DOM lives under `detection/` or `ui/`.

- `resolver/` — pure JVM. `BomEffectiveModelResolver` embeds Apache `maven-model-builder` to compute a BOM's fully-resolved effective model (parents merged, properties interpolated, nested BOM imports flattened). `BomVersionResolver` walks an ordered `List<Gav>` of BOMs and returns `ManagedVersionLookup.Found` / `NotFound`, always carrying an `uncheckedBoms` list so callers can tell "BOM says no" apart from "we couldn't check". `collectManagedVersions` is the same walk turned to a different question: instead of one target it builds every BOM's effective model and returns a `ManagedVersionCatalog` (a `Map<Ga, String>` of everything the chain manages, plus its own `uncheckedBoms`) so a caller can offer choices instead of answering a single lookup. It cannot share `resolveManagedVersion`'s early-return, which is exactly why it's a separate function: detection keeps the cheap single-target path, and only the Add dialog pays for the full walk. `LocalRepositoryModelResolver` is the model-builder plumbing that reads POMs from a local repo directory; it, `BomEffectiveModelResolver` and `BomVersionResolver` all take an `onMissingPom: (Gav) -> Unit` callback (default no-op) that fires immediately before a resolution failure, reporting the exact transitive coordinate — parent or nested BOM import — that was not on disk, which is what makes remote fetching possible without guessing what to fetch (see `detection/` below). `pomFileIn` maps a `Gav` to its standard `groupId/artifactId/version/artifactId-version.pom` path. `VersionRelation.kt` (`compareDeclaredToManaged`, backed by `maven-artifact`'s `ComparableVersion`) orders a declared version against the BOM-managed one using real Maven version semantics rather than lexical comparison; `INCOMPARABLE` is the safety valve for unresolved `${...}` properties and version ranges, which `ComparableVersion` would otherwise happily order into a confident-looking but meaningless verdict.

- `detection/` — PSI/DOM layer over `org.jetbrains.idea.maven`. `BomChainResolver` walks the parent chain of a `MavenDomProjectModel` collecting `<scope>import</scope><type>pom</type>` entries into `BomImport`s (each with the parent-chain `declaredVia` path used to render provenance), and returns them wrapped in a `BomChain(imports, truncatedAt)` — `truncatedAt` names every parent the walk could not get past — POM absent from the local repository, POM present but yielding no DOM model, or a `<parent>` naming no resolvable coordinate at all (recorded with `?` for the missing parts) — so a broken parent chain is reported rather than silently yielding a short-but-confident chain. `DependencyManagementScanner` picks out literal-version entries as `OverrideCandidate`s and reads the preceding XML comment as either a free-text reason or the suppress marker (`SUPPRESS_MARKER` in `PomComments.kt`). `OverrideDetector` composes the two (merging `truncatedAt` into its `uncheckedBoms`) and produces `DetectedOverride.Confirmed` (with `managedByChain` provenance, the actual BOM version, and a `VersionRelation` comparing the two — equal-version overrides are reported, not dropped, since a pin the BOM has exactly caught up to is the case this plugin exists to find), `DetectedOverride.Unmanaged` (chain fully readable, no BOM in it manages the artifact at all — carrying `checkedBoms` as the evidence; see invariants below for why this is reported rather than dropped), or `DetectedOverride.Inconclusive` (with the BOMs that couldn't be resolved). `MissingPomResolution.kt`'s `resolvingMissingPoms` is the retry loop wrapping all of that: it runs a caller-supplied `resolve` block inside `ReadAction.compute`, collects whatever GAVs it reports through `onMissingPom`, hands the concrete (non-`${...}`) ones to a fetcher — `RemotePomFetcher` by default — outside the read action, and repeats up to three rounds while a round downloads something new. `RemotePomFetcher` is the only class in the plugin that touches the network: it downloads `.pom` artifacts through the IDE's own Maven embedder (so mirrors, proxies and `settings-security.xml` credentials are applied by Maven's machinery, not reimplemented here), short-circuits to nothing on `MavenGeneralSettings.isWorkOffline()`, and VFS-refreshes what lands. `OverrideFormatting.kt` maps a `DetectedOverride` to an `OverrideVerdict` (`REDUNDANT`, `AHEAD_OF_BOM`, `BEHIND_BOM`, `NOT_COMPARABLE`, `INCONCLUSIVE`, `UNMANAGED`) plus label/explanation text; the verdict itself carries no icon, so the mapping stays testable as plain string logic and icon choice lives in `ui/`. `OverrideInspection` is the registered `LocalInspectionTool` that surfaces `REDUNDANT` and `BEHIND_BOM` as weak warnings with `RemoveOverrideQuickFix` / `SuppressOverrideQuickFix`, and `INCONCLUSIVE` with `SuppressOverrideQuickFix` only — `AHEAD_OF_BOM`, `NOT_COMPARABLE` and `UNMANAGED` register no problem at all (see invariants below). `OverrideMutations.kt` centralizes PSI writes (`removeOverride`, `setVersion`, `setReason`, `addOverride`) — always via `WriteCommandAction`, always with awareness that a snapshot `OverrideCandidate` may be stale (see the suppress-marker check in `setReason`). `ProjectOverrideScanner` walks every `pom.xml` in the project via `FilenameIndex` (deliberately not `MavenProjectsManager.projects`, so it works before Maven sync completes) for the tool window. `BomChainReport.kt`'s `buildBomChainReport` probes each BOM in the chain individually (rather than stopping at the first match, which is what normal detection does) so the "Show BOM Chain" dialog can show losers and unresolvable BOMs, not just the winner; it also carries the chain's `truncatedAt` through onto the report, without which the dialog would present a walk that stopped early as a complete chain and contradict the `Inconclusive` row that opened it. `DependencyCandidates` wraps a `ManagedVersionCatalog` with the rules relating the Add dialog's Group ID and Artifact ID fields — `groups()`, `artifactsIn()`, `allArtifactIds()`, `allCoordinates()`, `uniqueGroupFor()`, `managedVersionOf()`, `isComplete`, `unreadableBomCount` — and imports nothing from the IntelliJ Platform; that's deliberate; see invariants below for why it exists as its own class rather than living in the dialog.

- `ui/` — Swing tool window (`OverrideOverviewToolWindowFactory`) plus `AddOverrideDialog` / `EditOverrideDialog` / `BomChainDialog`. The panel's centre is the results table, unconditionally (see invariants below); its only global message is the offline notice along the bottom. `ManagedVersionHint` powers the live "currently managed at …" line in the Add/Edit dialogs; it's the same resolution as `OverrideDetector` but returns the raw `ManagedVersionLookup` because a hint has nothing to be Confirmed/Inconclusive about. `ManagedVersionHint.catalog` is the per-module counterpart of `lookup`, feeding `DependencyCandidates` in the Add dialog — same chain resolution, projected as everything the chain manages rather than one answer. The Add dialog's Group ID and Artifact ID fields are each a `TextFieldWithAutoCompletion` inside a `ComponentWithBrowseButton`: typing filters against the target module's BOM chain, the arrow button opens a searchable popup over the same candidates. Choosing a group narrows the artifact suggestions to it; typing an artifactId owned by exactly one group fills the group field in automatically (see invariants below for the ambiguous case). The version field prefills from what the BOM chain already manages the entered coordinate at, and a live hint line — read straight out of the already-loaded catalog, not a fresh chain resolution, so it keeps up with typing — reports what the entered version would mean using `compareDeclaredToManaged`: redundant, above the BOM, below it, or not comparable. The tool window's Status column renders each row's verdict as an icon, short label, and full-explanation tooltip; its row context menu also offers "Show BOM Chain" (opens `BomChainDialog` on a freshly built `BomChainReport`) and "Analyze Dependencies" (hands the artifact coordinate to IntelliJ's Maven Dependency Analyzer via `AnalyzeDependencyAction`, shown-but-disabled until the owning module has a resolved Maven project).

Extensions and dependencies (`com.intellij.java`, `org.jetbrains.idea.maven`) are declared in `src/main/resources/META-INF/plugin.xml`.

### Load-bearing invariants

- **`Ga` is groupId+artifactId only, no classifier/type.** BOM matching everywhere uses this pair — an artifact managed at different versions under different classifiers can be misclassified. Documented as a known v1 gap in `MavenCoordinates.kt`.
- **"Miss rather than false-safe."** A `<dependencyManagement>` entry with `scope=import` but a non-pom type is silently ignored by both the BOM chain resolver and the override scanner — never treated as either. Same principle drives `Inconclusive`: never claim "safe to remove" when any BOM in the chain wasn't verifiable. This is a security-relevant tool; a wrong "safe to remove" recommendation can silently reintroduce a patched CVE.
- **Parent resolution does relativePath first, then local-repo GAV.** Explicit-empty `<relativePath/>` (Spring Initializr's default) means "don't do relative lookup" and falls straight through to the repo lookup — do not shortcut this to the `../pom.xml` default, or detection silently breaks for essentially all non-multi-module Spring Boot projects. `MAX_PARENT_CHAIN_DEPTH` guards against cyclic parents.
- **`BomEffectiveModelResolver` must pass `System.getProperties()` to the model-builder request.** Without it, JDK-version-activated profiles in Apache-parented POMs (`org.apache:apache`'s `jdk9+` etc.) hard-fail and any BOM chain that touches them ends up `Inconclusive`.
- **XML comment creation goes through `createXmlComment` in `PomComments.kt`.** `XmlElementFactory` has no direct API for standalone comments; the workaround parses a throwaway wrapper. Comment text is sanitized (`--` → `- -`, trailing `-` padded) so any free-text reason produces well-formed XML — validation belongs at the UI layer, not here.
- **`OverrideVerdict.UNMANAGED` is silent in the editor, like `AHEAD_OF_BOM`.** The inspection has no BOM-based claim to make about a pin no BOM governs, and a weak warning on every hand-pinned transitive version would be loudest in exactly the projects that carry the most of them. `OverrideInspectionTest`'s "does not warn about an entry no BOM in the chain manages" guards it, and asserts on the word "BOM" rather than a BOM's name because the unmanaged explanation names no single BOM.
- **An override above its BOM version is deliberately silent in the editor.** `OverrideVerdict.AHEAD_OF_BOM` registers no inspection problem — the pin is still doing its job, so a warning there would be noise, not signal. It's visible only in the Override Overview tool window, which is an inventory rather than a list of complaints. `OverrideInspectionTest`'s "does not warn when the override is above the BOM version" case exists precisely so this absence doesn't regress silently — a future reader who assumes silence here is a bug should read that test before "fixing" it.
- **An override no BOM manages is reported as `Unmanaged`, not dropped — but only when the chain actually contains a BOM.** The two halves are one decision. Reporting it exists because the most common hand-written pin there is sits on a *transitive* dependency (`org.apache.qpid:proton-j` under `com.azure:azure-core-amqp`), pinned precisely *because* no BOM governs it; dropping those made the tool window silently incomplete on the entries most worth reviewing, while claiming to list every override. Gating on `bomChain.imports.isNotEmpty()` exists because without any BOM there is nothing to override: every literal-version `<dependencyManagement>` entry in the module would otherwise be reported, turning a plain dependency-management block into a page of findings that say nothing. `Inconclusive` still outranks `Unmanaged` when `unchecked` is non-empty — a chain we could not fully read might manage the artifact above the break, so "no BOM manages this" is a claim only a fully-read chain can support. `OverrideDetectorTest` pins all three branches (`reports a candidate no BOM in the chain manages as unmanaged`, `drops a candidate in a module whose chain imports no BOM at all`, `prefers inconclusive over unmanaged…`). Note what `Unmanaged` deliberately does *not* do: recommend anything. Whether such a pin still has an effect depends on the resolved dependency tree, which this plugin does not compute — hence the hand-off to "Analyze Dependencies" in its explanation text rather than a verdict.
- **`VersionRelation.INCOMPARABLE` produces no verdict-driven recommendation and no editor problem.** It's the same "miss rather than false-safe" reflex as `Inconclusive`: a declared version that can't be ordered against the managed one (an unresolved property, a version range) gets `OverrideVerdict.NOT_COMPARABLE` and no guess at whether it's redundant, ahead, or behind.
- **`ReadAction.compute` is not a way to get off the EDT** — it takes the read lock and runs on the calling thread. Every panel action that resolves a `VirtualFile` into a module, a POM model, or the projects tree must go through `executeOnPooledThread { ReadAction.compute { … } }` and hop back via `SwingUtilities.invokeLater` for the UI half. `ModuleUtilCore.findModuleForFile` (via `ProjectFileIndex`), `MavenDomUtil.getMavenDomProjectModel` (PSI from VFS) and `MavenProjectsManager.findProject` (lazily deserializes the projects tree from disk on first use) all trip `SlowOperations.assertSlowOperationsAreAllowed` on the EDT. This has been got wrong twice; `navigateTo` is the one deliberate exception, since it only reads `isValid`/`textOffset` off an already-resolved PSI element.
- **The Maven-sync state behind "Analyze Dependencies" is computed off the EDT and cached.** `OverrideOverviewPanel.refresh()` does the `MavenProjectsManager.findProject` probe on its pooled thread and stores the per-row result in `mavenSyncedRows`, so building the context menu needs no lookup at all. The cached value can go stale between refreshes; that's accepted, matching how the panel already tolerates snapshot staleness elsewhere (e.g. around `removeOverride`).
- **The tool window never withholds its table.** `populate` renders every scanned row, including ones whose version or BOM coordinate still reads `${foo.version}` because Maven property resolution was unavailable. Two narrower gates were tried and both removed: `MavenProjectsManager.isInitialized()` is false in a project that was never imported as a Maven project, where no sync is pending, Refresh changes nothing, and detection off `FilenameIndex` works fine — so it empties the panel permanently in projects it could still serve; and a `dependsOnUnresolvedProperty` count that replaced the table with an explanation when *every* row was affected turned out to hide the table permanently in real large projects (internal BOMs imported at `${revision}`, modules Maven never imported), where the rows are still the most useful thing the panel has. The lesson generalizes: a `${...} → ?` row is visibly incomplete, so the reader can discount it, whereas an empty panel is indistinguishable from "no overrides here" and gives them nothing to discount. Verdicts stay honest on their own — such a row lands on `NOT_COMPARABLE` or `INCONCLUSIVE`, never on a recommendation (see the `MavenPropertyResolver` invariant below). Do not re-add a suppression layer on top of that.
- **`MavenPropertyResolver.resolve` is a no-op until Maven sync has run.** Since IDEA 2026.2 it returns its input unchanged unless `MavenProjectsManager.isInitialized()`, so a `${...}` version reaches `DependencyManagementScanner` and `BomChainResolver` as literal text in a light test fixture and in a real IDE before the first sync completes. The plugin does not paper over this: unresolved text is `INCOMPARABLE`, so the override becomes `NOT_COMPARABLE`, and a BOM imported at a property version finds no POM in the local repo and lands in `uncheckedBoms` → `Inconclusive`. Both are the intended failure direction, and the two `leaves a property based … unresolved before Maven sync` tests pin that. Anyone tempted to hand-roll interpolation (e.g. via `MavenPropertyResolver.collectPropertyMapFromDOM`) is building a second, partial property resolver — parent-chain properties, profiles and `project.*` built-ins all have to come with it, or the result is a confident answer computed from half the properties.
- **An ambiguous artifactId never auto-fills a group.** `DependencyCandidates.uniqueGroupFor` returns null for both an unknown artifactId and, deliberately, an ambiguous one — more than one group in the module's BOM chain owns it. That's the same refuse-to-guess reflex behind `Inconclusive`: a future reader who "improves" it into picking the first match would make the Add dialog quietly wrong instead of visibly unhelpful. The full-coordinate dropdown (`AddOverrideDialog.chooseArtifact` with no group typed yet) is the intended way through an ambiguity, not a guess in `uniqueGroupFor`.
- **`DependencyCandidates` exists to keep logic out of the Swing layer.** This project leaves its dialogs and tool window hand-verified rather than unit-tested, which is only affordable while they hold nothing worth testing. The field-coupling rules (`groups()`, `artifactsIn()`, `uniqueGroupFor()`, …) are worth testing, so they live in a plain class instead of being inlined into `AddOverrideDialog` — resist the instinct to fold those few list operations back into the dialog for brevity.
- **"Analyze Dependencies" goes through `AbstractDependencyAnalyzerAction`, never `DependencyAnalyzerManager`.** The manager is `@ApiStatus.Internal`; calling it directly makes `./gradlew verifyPlugin` fail with `INTERNAL_API_USAGES` and fails the Marketplace review with it. `AnalyzeDependencyAction` subclasses the public abstract action instead and carries an already-resolved `Module` and `DAArtifact`, so the base class's `getModule`/`getDependencyData` hooks do no slow work when they run on the EDT. That constraint is why the module lookup still happens on a pooled thread in `OverrideOverviewPanel.analyzeDependencies` before the action is constructed.
- **`BomEffectiveModelResolver` memoizes per instance, and that instance must stay short-lived.** One inspection pass asks for the same BOM once per override in the file, so the cache turns N×M model builds into M. It is deliberately *not* hoisted to a project- or application-level cache: a POM in the local repository is only immutable for release versions, and a re-installed SNAPSHOT BOM answered from a stale model is precisely how this plugin would call an override "safe to remove" on evidence that no longer holds. `OverrideDetector.forProject` and `ManagedVersionHint.forProject` building a fresh resolver per call is what bounds the cache's lifetime — keep it that way.
- **Every registered inspection needs `src/main/resources/inspectionDescriptions/<shortName>.html`.** The platform locates it by the `shortName` in `plugin.xml` (`MavenDependencyOverride`), and without it the Settings | Editor | Inspections page shows no description at all. Renaming the inspection's `shortName` without renaming the file silently breaks it.
- **The Add dialog's version prefill only works because it ships with the live verdict next to it.** Prefilling what the BOM already manages, on its own, would walk the user straight into creating the exact redundant pin this plugin exists to flag. The dependency runs one way: anyone removing the verdict line in `updateHint` must remove `maybePrefillVersion` with it. The reverse is fine — dropping the prefill and keeping the verdict just leaves the hint describing whatever version the user typed themselves.
- **`OverrideInspection` never fetches, and that asymmetry is the design.** Everything else (tool window, both dialogs, the BOM chain view) resolves through `resolvingMissingPoms`; the inspection resolves with the no-op default. It runs synchronously per file on every edit, so a network round-trip there is editor latency and repository load. The tool window answering confidently where the editor still says `Inconclusive` is expected, not a bug.
- **Missing POMs are reported, never fetched in place.** `LocalRepositoryModelResolver.resolve` and `BomChainResolver.resolveParentViaLocalRepository` report the coordinate and still fail; fetching happens in `resolvingMissingPoms`, outside the read action. Two reasons, both load-bearing: a synchronous VFS refresh throws under the read lock, and `BomModelResult.Failure` names the BOM that failed to build rather than the POM that was missing — so an on-demand fetcher would re-request artifacts it already has and never converge.
- **`RemotePomFetcher` must not reimplement mirrors, proxies or credentials.** It hands the repository list to the IDE's Maven server, which applies `settings.xml` mirrors, proxies and authentication inside Maven's own `RepositorySystem`. Reimplementing any of that here — mirror selection, `settings-security.xml` decryption — is the class of correctness bug the design doc rules out by embedding Maven's own machinery. Offline mode is honored before any embedder is obtained: `fetch` returns an empty set immediately when `MavenGeneralSettings.isWorkOffline` is set, so no request is ever built.
- **`RemotePomFetcher` uses the `@ApiStatus.Obsolete` `MavenEmbeddersManager` on purpose, not out of neglect.** Its modern replacement, `MavenEmbedderWrappers`/`MavenEmbedderWrappersManager`, is class-level `@ApiStatus.Internal` on 2026.2 — `./gradlew verifyPlugin` fails on it with `INTERNAL_API_USAGES`, and so does the Marketplace review. Obsolete-but-allowed beats modern-but-rejected. Anyone "modernizing" this must re-run `verifyPlugin` and see it pass first; same constraint recorded for `AnalyzeDependencyAction`.
- **A coordinate still containing `${...}` is never fetched.** `Gav.isConcrete()` gates `resolvingMissingPoms`, because `MavenPropertyResolver.resolve` returns its input unchanged until Maven sync has run (see the invariant above). Before the first sync, a BOM or parent declared at a property version reaches the resolver as a placeholder; that is a coordinate we do not know yet, not a miss we can download. Dropping the filter would send guaranteed-404 requests built from placeholder text and, worse, make every round re-report the same unfetchable coordinate until the round budget ran out.
- **A truncated parent chain is `Inconclusive`, not a short chain.** `BomChain.truncatedAt` exists because a parent POM missing from the local repository used to end the walk silently, letting `OverrideDetector` report a confident "nothing manages this" for an artifact a BOM above the break manages. All three ways the walk can stop report through it — POM absent, POM present but yielding no DOM model, `<parent>` with no resolvable coordinate — and the last two are as load-bearing as the first: since `RemotePomFetcher` writes POMs into the repository itself, a partially-written or error-bodied file is a real way to get a `Confirmed` verdict on a chain that was never fully walked. `OverrideDetectorTest`'s truncated-chain case and `BomChainResolverTest`'s three truncation cases guard it. The only unreported exit is `MAX_PARENT_CHAIN_DEPTH`, which fires solely on a cyclic or absurdly deep chain Maven itself cannot build.
- **The `ProgressManager.runProcess` wrapper around `runBlockingCancellable` in `RemotePomFetcher` is not redundant.** With neither a `ProgressIndicator` nor a `Job` on the thread, `runBlockingCancellable` calls `LOG.error("There is no ProgressIndicator or Job in this thread…")`. The fetch still completes — which is exactly why the wrapper looks removable — but a released IDE turns `Logger.error` into the red "IDE internal error" balloon naming this plugin on every use of the feature, and `TestLoggerFactory` turns it into a test failure. `ApplicationManager.executeOnPooledThread` passes `withContextJob = false`, and several call sites submit from plain AWT dispatch, so there is nothing there by default. `runBlockingMaybeCancellable` and `indicatorRunBlockingCancellable` are both `@Deprecated` as platform-internal and are not alternatives.

## Testing

Tests split by what the class under test touches, not by directory: `resolver/` is entirely plain JUnit, no `BasePlatformTestCase`, since nothing there touches the IntelliJ Platform. Under `detection/` the rule is the same rather than an exception to it — a test extends `BasePlatformTestCase` exactly when its class under test touches PSI/DOM, and stays plain JUnit when the class under test is itself platform-free, as `BomChainReportTest` and `DependencyCandidatesTest` currently are. `MissingPomResolutionTest` is the one deliberate exception: `resolvingMissingPoms` touches no PSI/DOM but takes the read lock through `ReadAction.compute`, which needs a real application, so it extends `BasePlatformTestCase` anyway — its own KDoc says so, to stop a future reader "correcting" it back to plain JUnit. `ui/` has no tests at all yet; its dialogs and tool window are hand-verified, which is the point of keeping logic like `DependencyCandidates` out of them. Fixture POMs live at `src/test/resources/fixtures/local-repo/` in real local-repo layout — `OverrideInspectionTest` shows the pattern of injecting a fixture-backed `OverrideDetector` via `OverrideInspection { OverrideDetector(BomVersionResolver(fixtureDir)) }` instead of relying on `MavenProjectsManager` inside a lightweight sandbox.
