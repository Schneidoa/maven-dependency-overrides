# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this plugin does

IntelliJ Platform plugin that flags Maven `<dependencyManagement>` version overrides that have become stale because an imported BOM chain has caught up (typical case: a CVE-driven pin that Spring Boot's BOM now provides at or above the pinned version). Detection is local-only — it reads whatever POMs are already in the user's local Maven repository — and refuses to answer confidently when a BOM in the chain can't be resolved there (`Inconclusive` vs. `Confirmed`).

## Build & run

```bash
./gradlew check                # unit tests + platform tests (this is what .run/Run Tests wraps)
./gradlew test --tests "cloud.schneidoa.detection.OverrideDetectorTest"                       # single class
./gradlew test --tests "cloud.schneidoa.detection.OverrideDetectorTest.test*confirmed*"       # single test (backticked names → globs)
./gradlew runIde               # launch a sandbox IDE with the plugin loaded (for manual verification)
./gradlew verifyPlugin         # IntelliJ plugin-verifier compatibility check
```

Target platform is pinned in `build.gradle.kts` (`intellijIdea("2026.2.1")`). The `prepareTestSandbox` task disables the bundled Vue.js plugin — leave that in place; the comment there explains why, and TestLoggerFactory's "logged errors fail the test" behavior is deliberately kept on as a safety net.

## Branches and releases

Work goes on `develop`; `main` is the release branch and receives merges from `develop` only. `.github/workflows/build.yml` runs `check buildPlugin verifyPlugin` on every `develop` push and every PR into either branch. `.github/workflows/release.yml` runs on `main` and does the whole release: patch changelog → same build gate → `publishPlugin` → tag `v<version>` → GitHub Release → changelog PR back to `develop`.

Two things about that flow are load-bearing. **The `version` in `gradle.properties` is the entire release trigger**, and the `v<version>` tag is the idempotence guard: a push to `main` whose version is already tagged releases nothing and reports as skipped, which is what makes merging a docs fix into `main` harmless. The tag is therefore written *after* a successful Marketplace upload, never before — a tag on a release that didn't happen would silently block the retry. **A version with a pre-release suffix routes itself**: `channels` in `build.gradle.kts` sends `0.3.0-beta.1` to the `eap` channel and a plain `0.3.0` to the default one, and the workflow marks the GitHub Release accordingly. Both halves read the same `-` in the version string; changing one without the other splits the two apart.

## Architecture

Package `cloud.schneidoa` splits into two layers with a hard rule: everything under `resolver/` must stay free of IntelliJ Platform APIs so it stays unit-testable against fixture POMs; anything that touches PSI/DOM lives under `detection/` or `ui/`.

- `resolver/` — pure JVM. `BomEffectiveModelResolver` embeds Apache `maven-model-builder` to compute a BOM's fully-resolved effective model (parents merged, properties interpolated, nested BOM imports flattened). `BomVersionResolver` walks an ordered `List<Gav>` of BOMs and returns `ManagedVersionLookup.Found` / `NotFound`, always carrying an `uncheckedBoms` list so callers can tell "BOM says no" apart from "we couldn't check". `collectManagedVersions` is the same walk turned to a different question: instead of one target it builds every BOM's effective model and returns a `ManagedVersionCatalog` (a `Map<Ga, String>` of everything the chain manages, plus its own `uncheckedBoms`) so a caller can offer choices instead of answering a single lookup. It cannot share `resolveManagedVersion`'s early-return, which is exactly why it's a separate function: detection keeps the cheap single-target path, and only the Add dialog pays for the full walk. `LocalRepositoryModelResolver` is the model-builder plumbing that reads POMs from a local repo directory. `pomFileIn` maps a `Gav` to its standard `groupId/artifactId/version/artifactId-version.pom` path. `VersionRelation.kt` (`compareDeclaredToManaged`, backed by `maven-artifact`'s `ComparableVersion`) orders a declared version against the BOM-managed one using real Maven version semantics rather than lexical comparison; `INCOMPARABLE` is the safety valve for unresolved `${...}` properties and version ranges, which `ComparableVersion` would otherwise happily order into a confident-looking but meaningless verdict.

- `detection/` — PSI/DOM layer over `org.jetbrains.idea.maven`. `BomChainResolver` walks the parent chain of a `MavenDomProjectModel` collecting `<scope>import</scope><type>pom</type>` entries into `BomImport`s (each with the parent-chain `declaredVia` path used to render provenance). `DependencyManagementScanner` picks out literal-version entries as `OverrideCandidate`s and reads the preceding XML comment as either a free-text reason or the suppress marker (`SUPPRESS_MARKER` in `PomComments.kt`). `OverrideDetector` composes the two and produces `DetectedOverride.Confirmed` (with `managedByChain` provenance, the actual BOM version, and a `VersionRelation` comparing the two — equal-version overrides are reported, not dropped, since a pin the BOM has exactly caught up to is the case this plugin exists to find) or `DetectedOverride.Inconclusive` (with the BOMs that couldn't be resolved). `OverrideFormatting.kt` maps a `DetectedOverride` to an `OverrideVerdict` (`REDUNDANT`, `AHEAD_OF_BOM`, `BEHIND_BOM`, `NOT_COMPARABLE`, `INCONCLUSIVE`) plus label/explanation text; the verdict itself carries no icon, so the mapping stays testable as plain string logic and icon choice lives in `ui/`. `OverrideInspection` is the registered `LocalInspectionTool` that surfaces `REDUNDANT` and `BEHIND_BOM` as weak warnings with `RemoveOverrideQuickFix` / `SuppressOverrideQuickFix`, and `INCONCLUSIVE` with `SuppressOverrideQuickFix` only — `AHEAD_OF_BOM` and `NOT_COMPARABLE` register no problem at all (see invariants below). `OverrideMutations.kt` centralizes PSI writes (`removeOverride`, `setVersion`, `setReason`, `addOverride`) — always via `WriteCommandAction`, always with awareness that a snapshot `OverrideCandidate` may be stale (see the suppress-marker check in `setReason`). `ProjectOverrideScanner` walks every `pom.xml` in the project via `FilenameIndex` (deliberately not `MavenProjectsManager.projects`, so it works before Maven sync completes) for the tool window. `BomChainReport.kt`'s `buildBomChainReport` probes each BOM in the chain individually (rather than stopping at the first match, which is what normal detection does) so the "Show BOM Chain" dialog can show losers and unresolvable BOMs, not just the winner. `DependencyCandidates` wraps a `ManagedVersionCatalog` with the rules relating the Add dialog's Group ID and Artifact ID fields — `groups()`, `artifactsIn()`, `allArtifactIds()`, `allCoordinates()`, `uniqueGroupFor()`, `managedVersionOf()`, `isComplete`, `unreadableBomCount` — and imports nothing from the IntelliJ Platform; that's deliberate; see invariants below for why it exists as its own class rather than living in the dialog.

- `ui/` — Swing tool window (`OverrideOverviewToolWindowFactory`) plus `AddOverrideDialog` / `EditOverrideDialog` / `BomChainDialog`. `ManagedVersionHint` powers the live "currently managed at …" line in the Add/Edit dialogs; it's the same resolution as `OverrideDetector` but returns the raw `ManagedVersionLookup` because a hint has nothing to be Confirmed/Inconclusive about. `ManagedVersionHint.catalog` is the per-module counterpart of `lookup`, feeding `DependencyCandidates` in the Add dialog — same chain resolution, projected as everything the chain manages rather than one answer. The Add dialog's Group ID and Artifact ID fields are each a `TextFieldWithAutoCompletion` inside a `ComponentWithBrowseButton`: typing filters against the target module's BOM chain, the arrow button opens a searchable popup over the same candidates. Choosing a group narrows the artifact suggestions to it; typing an artifactId owned by exactly one group fills the group field in automatically (see invariants below for the ambiguous case). The version field prefills from what the BOM chain already manages the entered coordinate at, and a live hint line — read straight out of the already-loaded catalog, not a fresh chain resolution, so it keeps up with typing — reports what the entered version would mean using `compareDeclaredToManaged`: redundant, above the BOM, below it, or not comparable. The tool window's Status column renders each row's verdict as an icon, short label, and full-explanation tooltip; its row context menu also offers "Show BOM Chain" (opens `BomChainDialog` on a freshly built `BomChainReport`) and "Analyze Dependencies" (hands the artifact coordinate to IntelliJ's Maven Dependency Analyzer via `AnalyzeDependencyAction`, shown-but-disabled until the owning module has a resolved Maven project).

Extensions and dependencies (`com.intellij.java`, `org.jetbrains.idea.maven`) are declared in `src/main/resources/META-INF/plugin.xml`.

### Load-bearing invariants

- **`Ga` is groupId+artifactId only, no classifier/type.** BOM matching everywhere uses this pair — an artifact managed at different versions under different classifiers can be misclassified. Documented as a known v1 gap in `MavenCoordinates.kt`.
- **"Miss rather than false-safe."** A `<dependencyManagement>` entry with `scope=import` but a non-pom type is silently ignored by both the BOM chain resolver and the override scanner — never treated as either. Same principle drives `Inconclusive`: never claim "safe to remove" when any BOM in the chain wasn't verifiable. This is a security-relevant tool; a wrong "safe to remove" recommendation can silently reintroduce a patched CVE.
- **Parent resolution does relativePath first, then local-repo GAV.** Explicit-empty `<relativePath/>` (Spring Initializr's default) means "don't do relative lookup" and falls straight through to the repo lookup — do not shortcut this to the `../pom.xml` default, or detection silently breaks for essentially all non-multi-module Spring Boot projects. `MAX_PARENT_CHAIN_DEPTH` guards against cyclic parents.
- **`BomEffectiveModelResolver` must pass `System.getProperties()` to the model-builder request.** Without it, JDK-version-activated profiles in Apache-parented POMs (`org.apache:apache`'s `jdk9+` etc.) hard-fail and any BOM chain that touches them ends up `Inconclusive`.
- **XML comment creation goes through `createXmlComment` in `PomComments.kt`.** `XmlElementFactory` has no direct API for standalone comments; the workaround parses a throwaway wrapper. Comment text is sanitized (`--` → `- -`, trailing `-` padded) so any free-text reason produces well-formed XML — validation belongs at the UI layer, not here.
- **An override above its BOM version is deliberately silent in the editor.** `OverrideVerdict.AHEAD_OF_BOM` registers no inspection problem — the pin is still doing its job, so a warning there would be noise, not signal. It's visible only in the Override Overview tool window, which is an inventory rather than a list of complaints. `OverrideInspectionTest`'s "does not warn when the override is above the BOM version" case exists precisely so this absence doesn't regress silently — a future reader who assumes silence here is a bug should read that test before "fixing" it.
- **`VersionRelation.INCOMPARABLE` produces no verdict-driven recommendation and no editor problem.** It's the same "miss rather than false-safe" reflex as `Inconclusive`: a declared version that can't be ordered against the managed one (an unresolved property, a version range) gets `OverrideVerdict.NOT_COMPARABLE` and no guess at whether it's redundant, ahead, or behind.
- **`ReadAction.compute` is not a way to get off the EDT** — it takes the read lock and runs on the calling thread. Every panel action that resolves a `VirtualFile` into a module, a POM model, or the projects tree must go through `executeOnPooledThread { ReadAction.compute { … } }` and hop back via `SwingUtilities.invokeLater` for the UI half. `ModuleUtilCore.findModuleForFile` (via `ProjectFileIndex`), `MavenDomUtil.getMavenDomProjectModel` (PSI from VFS) and `MavenProjectsManager.findProject` (lazily deserializes the projects tree from disk on first use) all trip `SlowOperations.assertSlowOperationsAreAllowed` on the EDT. This has been got wrong twice; `navigateTo` is the one deliberate exception, since it only reads `isValid`/`textOffset` off an already-resolved PSI element.
- **The Maven-sync state behind "Analyze Dependencies" is computed off the EDT and cached.** `OverrideOverviewPanel.refresh()` does the `MavenProjectsManager.findProject` probe on its pooled thread and stores the per-row result in `mavenSyncedRows`, so building the context menu needs no lookup at all. The cached value can go stale between refreshes; that's accepted, matching how the panel already tolerates snapshot staleness elsewhere (e.g. around `removeOverride`).
- **`MavenPropertyResolver.resolve` is a no-op until Maven sync has run.** Since IDEA 2026.2 it returns its input unchanged unless `MavenProjectsManager.isInitialized()`, so a `${...}` version reaches `DependencyManagementScanner` and `BomChainResolver` as literal text in a light test fixture and in a real IDE before the first sync completes. The plugin does not paper over this: unresolved text is `INCOMPARABLE`, so the override becomes `NOT_COMPARABLE`, and a BOM imported at a property version finds no POM in the local repo and lands in `uncheckedBoms` → `Inconclusive`. Both are the intended failure direction, and the two `leaves a property based … unresolved before Maven sync` tests pin that. Anyone tempted to hand-roll interpolation (e.g. via `MavenPropertyResolver.collectPropertyMapFromDOM`) is building a second, partial property resolver — parent-chain properties, profiles and `project.*` built-ins all have to come with it, or the result is a confident answer computed from half the properties.
- **An ambiguous artifactId never auto-fills a group.** `DependencyCandidates.uniqueGroupFor` returns null for both an unknown artifactId and, deliberately, an ambiguous one — more than one group in the module's BOM chain owns it. That's the same refuse-to-guess reflex behind `Inconclusive`: a future reader who "improves" it into picking the first match would make the Add dialog quietly wrong instead of visibly unhelpful. The full-coordinate dropdown (`AddOverrideDialog.chooseArtifact` with no group typed yet) is the intended way through an ambiguity, not a guess in `uniqueGroupFor`.
- **`DependencyCandidates` exists to keep logic out of the Swing layer.** This project leaves its dialogs and tool window hand-verified rather than unit-tested, which is only affordable while they hold nothing worth testing. The field-coupling rules (`groups()`, `artifactsIn()`, `uniqueGroupFor()`, …) are worth testing, so they live in a plain class instead of being inlined into `AddOverrideDialog` — resist the instinct to fold those few list operations back into the dialog for brevity.
- **"Analyze Dependencies" goes through `AbstractDependencyAnalyzerAction`, never `DependencyAnalyzerManager`.** The manager is `@ApiStatus.Internal`; calling it directly makes `./gradlew verifyPlugin` fail with `INTERNAL_API_USAGES` and fails the Marketplace review with it. `AnalyzeDependencyAction` subclasses the public abstract action instead and carries an already-resolved `Module` and `DAArtifact`, so the base class's `getModule`/`getDependencyData` hooks do no slow work when they run on the EDT. That constraint is why the module lookup still happens on a pooled thread in `OverrideOverviewPanel.analyzeDependencies` before the action is constructed.
- **`BomEffectiveModelResolver` memoizes per instance, and that instance must stay short-lived.** One inspection pass asks for the same BOM once per override in the file, so the cache turns N×M model builds into M. It is deliberately *not* hoisted to a project- or application-level cache: a POM in the local repository is only immutable for release versions, and a re-installed SNAPSHOT BOM answered from a stale model is precisely how this plugin would call an override "safe to remove" on evidence that no longer holds. `OverrideDetector.forProject` and `ManagedVersionHint.forProject` building a fresh resolver per call is what bounds the cache's lifetime — keep it that way.
- **Every registered inspection needs `src/main/resources/inspectionDescriptions/<shortName>.html`.** The platform locates it by the `shortName` in `plugin.xml` (`MavenDependencyOverride`), and without it the Settings | Editor | Inspections page shows no description at all. Renaming the inspection's `shortName` without renaming the file silently breaks it.
- **The Add dialog's version prefill only works because it ships with the live verdict next to it.** Prefilling what the BOM already manages, on its own, would walk the user straight into creating the exact redundant pin this plugin exists to flag. The dependency runs one way: anyone removing the verdict line in `updateHint` must remove `maybePrefillVersion` with it. The reverse is fine — dropping the prefill and keeping the verdict just leaves the hint describing whatever version the user typed themselves.

## Testing

Tests split by what the class under test touches, not by directory: `resolver/` is entirely plain JUnit, no `BasePlatformTestCase`, since nothing there touches the IntelliJ Platform. Under `detection/` the rule is the same rather than an exception to it — a test extends `BasePlatformTestCase` exactly when its class under test touches PSI/DOM, and stays plain JUnit when the class under test is itself platform-free, as `BomChainReportTest` and `DependencyCandidatesTest` currently are. `ui/` has no tests at all yet; its dialogs and tool window are hand-verified, which is the point of keeping logic like `DependencyCandidates` out of them. Fixture POMs live at `src/test/resources/fixtures/local-repo/` in real local-repo layout — `OverrideInspectionTest` shows the pattern of injecting a fixture-backed `OverrideDetector` via `OverrideInspection { OverrideDetector(BomVersionResolver(fixtureDir)) }` instead of relying on `MavenProjectsManager` inside a lightweight sandbox.
