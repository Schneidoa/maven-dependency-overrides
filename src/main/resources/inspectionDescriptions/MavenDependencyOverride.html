Reports <dependencyManagement> version overrides that an imported BOM chain has caught up with, and ones that hold a dependency below the version the BOM already provides.

The typical case is a version pinned by hand ahead of a CVE fix, which the project's own dependency management — Spring Boot's BOM, for instance — later shipped at the same version or newer. The pin has become redundant, but nothing points that out, so it stays in the POM and quietly holds the dependency back at the next upgrade.

Example, with spring-boot-dependencies managing Jackson at 2.21.2:


  <dependencyManagement>
    <dependencies>
      <dependency>
        <groupId>com.fasterxml.jackson.core</groupId>
        <artifactId>jackson-databind</artifactId>
        <version>2.21.2</version> <!-- reported: the BOM manages this exact version -->
      </dependency>
    </dependencies>
  </dependencyManagement>

An override that still raises the version above what the BOM chain provides is not reported: the pin is doing its job. Neither is one whose version cannot be ordered against the BOM's at all, such as an unresolved property or a version range. Both remain visible in the Maven Overrides tool window, which lists every override rather than only the ones worth acting on.

Detection reads BOM POMs from the local Maven repository and never goes to the network. When a BOM in the chain is missing there, the override is reported as inconclusive and no removal fix is offered — a wrong "safe to remove" suggestion could silently reintroduce a patched CVE.

Use Remove dependency override to delete the entry, or Suppress this override warning to keep it and mark it with a comment so it is skipped from then on.
